# GameStore — план обучения и разработки

План под pet-проект и подготовку к стажировке **«Разработчик .NET» (Т-Банк)**.  
Статус выполнения — в [`progress.md`](./progress.md). Этот файл — **roadmap**, не дневник.

---

## Принципы

1. **Backend first.** API, EF Core, SQL, тесты — приоритет. Фронт минимальный и позже.
2. **Сначала довести то, что уже есть**, потом расширять домен (Users → Auth → Orders).
3. **Учиться на своём коде:** каждый этап = фича в GameStore + 1–2 концепции для собеса.
4. **Параллельно:** SQL (ежедневно) + алгоритмы (несколько задач в неделю) + Git на этом репо.
5. Не копировать «идеальную» enterprise-архитектуру раньше времени. Слои появляются, когда боль от их отсутствия уже понятна.

## Этап A — Стабилизация каталога (3–5 дней)

Цель: честный, предсказуемый CRUD без «скрытых багов».

**Сделать:**

1. Добавить `Id` (и при необходимости `CategoryId`) в response DTO.
2. `Include(g => g.Category)` при чтении игр (или проекция в DTO).
3. Явная проверка существования категории при create/update/patch category → 404/400, не 500.
4. Category: `PUT` и/или `DELETE` (с правилом: нельзя удалить категорию с играми — или cascade, но осознанно).
5. Починить integration-тесты под реальные DTO; добавить тесты категорий.
6. `.gitignore` (bin/obj, user secrets, IDE); вынести секреты из коммита (`dotnet user-secrets` или `appsettings.Development.json` в ignore).
7. Первый осмысленный git-коммит (и дальше — мелкие коммиты после логических кусков).

**Закрепляешь:** HTTP-семантика, навигационные свойства EF, FK, смысл DTO, зачем тесты ломаются при смене контракта.

**Критерий готовности:** `dotnet test` зелёный; в Swagger полный сценарий category → game → list с именем категории.

## Этап B — SQL на своей базе (параллельно, постоянно)

Не ждать Orders. Уже сейчас:

```sql
-- примеры на текущей схеме
SELECT g."Name", c."Name" AS category, g."Price"
FROM "Games" g
JOIN "Categories" c ON c."Id" = g."CategoryId"
WHERE g."Price" < 1000
ORDER BY g."Price";
```

Мини-программа на неделю — в `progress.md` (трек B).  
Когда появятся Orders — добавить агрегаты «топ покупателей», «игры без покупок».

**Для Т-Банка:** SQL часто слабое место у Unity→.NET; это конкурентное преимущество, если потренировать руки.

## Этап D — Users + Auth (5–7 дней)

Минимум для «взрослого» backend:

1. Сущность `User` (email/username, password hash — не plaintext).
2. Регистрация / логин.
3. JWT: выдача токена, `[Authorize]` / `RequireAuthorization` на защищённых эндпоинтах.
4. Хотя бы роль или флаг: обычный пользователь vs admin (создание игр — только admin, либо пока все авторизованные).

**Закрепляешь:** middleware pipeline, claims, почему пароль хешируем, lifetimes DI для auth-сервисов.

**Не обязательно сразу Identity UI** — можно начать с ручного JWT + ASP.NET Auth middleware. Identity — если останется время и интерес.

## Этап E — Orders (5–7 дней)

Домен:

```text
User 1──* Order 1──* OrderItem *──1 Game
```

Сценарий:

1. `POST /orders` — оформить заказ (список gameId + qty или «купить одну игру»).
2. `GET /orders` — свои заказы (только текущего пользователя).
3. `GET /orders/{id}` — детали.
4. Транзакция: либо весь заказ создаётся, либо ничего.
5. (Опционально) библиотека купленных игр — `GET /library`.

**Закрепляешь:** связи EF, транзакции, авторизация на уровне ресурса («чужой заказ — 403/404»).

## Что сознательно откладываем

| Тема | Почему позже |
|------|--------------|
| React / TypeScript | Съест время, нужен .NET |
| Microservices / RabbitMQ | На стажировке дадут с наставником; в pet — overkill |
| Controllers вместо Minimal APIs | Текущий стиль нормален; Controllers можно попробовать на одном модуле для сравнения |
| Идеальный Clean Architecture / CQRS | Слои Service/Repo достаточно для уровня стажёра |
| Kubernetes, облако | Не цель до оффера |
